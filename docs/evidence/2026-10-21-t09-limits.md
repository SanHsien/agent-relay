# T-20261021-09 實測：並發、每日上限與防重跑（2026-10-21）

**拓撲**：指揮者與 machine-b（同一台主機上的第二份 clone），信件有簽章。machine-b 的設定是 `dispatch.max_concurrent: 2`、`daily_limit: 30`。

## 做法

1. 指揮者寄 5 封 hermes 小工單（`T-09 concurrency 1..5`），內容都是在 `calc-demo` 建一個檔案。
2. 在 machine-b 同時啟動 5 個 `relay dispatch` 行程，模擬門鈴開了 5 個分頁。
3. 8 秒後，對第 1 封再觸發一次 `relay dispatch`。

## 結果

**重複觸發被拒**：`exit 2`，訊息為 `error: 20261020T232044604Z-1abfef is already being run here (pid 64060)`。這次觸發沒有寄回信，也沒有 ack。

**第 8 秒的狀態**：`runs/.slots/` 底下有 `slot-0`、`slot-1`。

| 工單 | lease phase |
| --- | --- |
| 1abfef | running |
| e6ddaf | running |
| 0303c9 | queued |
| de04c6 | queued |
| 180d8a | queued |

**5 封全部 `status: ok`**，各自由 relay 完成 commit、通過閘門並推送。工人實際的執行區間如下：開始時間取 `argv.json` 的 mtime，結束時間取 `output.log` 的 mtime（epoch 秒）。

| 工單 | 開始 | 結束 |
| --- | --- | --- |
| 1abfef | …482 | …548 |
| e6ddaf | …482 | …552 |
| 0303c9 | …557 | …624 |
| de04c6 | …557 | …618 |
| 180d8a | …633 | …690 |

任一時刻最多只有 2 個工人在執行。每當一個名額釋放，排隊中的工單會在約 5 秒內（輪詢間隔 15 秒以內）接手。

## 實測發現並修正的 bug

machine-b 的 `relay.log` 出現 4 次下面的錯誤：

```text
dispatch pull failed: git -c merge.directoryRenames=false pull --rebase --autostash --quiet failed: fatal: Cannot rebase onto multiple branches.
```

原因是 5 個分頁同時 `git pull` 同一份 store clone，彼此搶寫 `FETCH_HEAD` 和 `index.lock`。這次 dispatch 會退回使用本機副本，5 封回信也都送到了；但結尾的 commit／push 同樣可能互撞。

修正（commit `96f8174`）：`gitsync` 的 pull、commit、push、sync 都改成先取得 `.git/agent-relay-sync.lock`。這是 O_EXCL 鎖檔，同一 thread 內可重入，超過 15 分鐘視為殘留。

回歸測試 `test_concurrent_processes_on_one_clone` 用 5 個行程同時 sync 同一份 clone：

- 拿掉鎖時，4 個行程失敗，錯誤為 `index.lock: File exists`；
- 加上鎖後，5 個全部成功。

## 單元測試

`tests/test_dispatch.py::LimitTests` 涵蓋：

- 名額的取得、釋放與用完；
- 回收已死行程留下的名額；
- 5 執行緒、`max_concurrent=2` 時，同時執行的工人數峰值等於 2（連跑 3 次都穩定）；
- `daily_limit`；
- 同一張工單只能有一個工人，`--force` 也不例外。
