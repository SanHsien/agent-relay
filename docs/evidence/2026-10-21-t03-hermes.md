## 1. 事前探測：Hermes 單次模式的邊界

| 探測 | 結果 |
| --- | --- |
| `hermes -z ... --in . -t file` 修一個 bug | 成功改檔，exit 0，`--usage-file` 寫出用量 JSON |
| 同上，要求跑 shell | 失敗：工具只有 `patch`、`read_file`、`search_files`、`write_file` |
| 同上，寫 `../outside.txt` | **成功寫出**：`-t file` 本身不限制路徑 |
| 加 `HERMES_WRITE_SAFE_ROOT=<repo>` 再寫 `../outside.txt` | 被擋：`Write denied: '...outside.txt' is outside HERMES_WRITE_SAFE_ROOT (...)` |

`-z` 的說明寫明會自動略過核可，所以 relay 一定要同時設工具組與寫入根目錄（SPEC §7）。在一般 repo 裡，`.git/hooks` 位於寫入根目錄內，仍然寫得進去。relay 的 worktree 則不同：`.git` 是指向主 repo 的檔案，hooks 在根目錄外；改了 `.git` 指標的話，relay 不會 commit。

## 3. 實測中發現並修正的 bug

收件端第一次同步回信失敗，`relay.log` 記錄：

```text
dispatch sync failed: git commit --quiet -m relay: claude-code dispatch ... -- mailboxes claims audit failed:
error: pathspec 'claims' did not match any file(s) known to git
```

原因：store 裡留著空的 `claims/` 資料夾（之前的簽出鎖都已釋放），index 與 HEAD 都沒有它，`git commit -- claims` 因此失敗，回信只停在收件端的暫存區。之前的派工都帶簽出鎖，所以沒踩到。

修正：`gitsync.commit` 只把 index 或 HEAD 裡有的資料夾放進 commit pathspec，並加回歸測試 `test_empty_shared_folder_does_not_break_commit`。修正後在 machine-b 執行 `relay sync`，回信隨即送達指揮者。
